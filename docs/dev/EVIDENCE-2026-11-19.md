### The one FAIL: alley step 13. Pre-existing, a check bug on Windows only, not a flake

```
alley check: FAIL 13. game 1 of the final won: "Game 1 to you · 1-0"; the save keeps it ("bracketgames 0 1 3 0") and reads it back (games 0-1, the last loser side 0)
```

The same line is in `build/qa-win/checks-bugs/baseline-qa-final-alley/log.txt` (the Nov 12 build) and in Part B's
run.

- **The cause (CONFIRMED).** `DuelController.AlleyCheck.cs` builds `gamesLine` from `SaveText().Split('\n')`. It then
  requires `gamesLine == $"bracketgames {A} {B} 3 {last}"`.
- On Windows, `Brackets.Write` uses `StringBuilder.AppendLine`, so every line of the save ends in `\r\n`. In this run's
  save (`checks/alley/mods/save/profile.txt`) all 552 lines do. So `gamesLine` is `"bracketgames 0 1 3 0\r"`, and the
  comparison can never pass on Windows.
- The harness's version of this test trims the line (`BracketStudy.cs`, `...?.Trim()`) and passes: "Bo3 save
  mid-series: ... "bracketgames 0 1 3 0"".
- **The game is fine.** The values it reads back (games 0-1, last loser side 0) agree with "Game 1 to you · 1-0",
  with you on side B. The next steps on the same reloaded save pass: the pips "○ ○" over "● ○", game 2 with no toss,
  game 2 lost 1-1, and game 3 where you choose.
- **Verdict:** pre-existing, deterministic, Windows-only, in the check. Fix: `.TrimEnd('\r')` on `gamesLine` (not
  done: I don't fix).
- Side note: the owner's own Windows save (the copy in `build/cardrefresh/saves/`) is CRLF too, and it loads fine.

## Do the new steps bite? (each read against its assertion)

- **alley 4b (8 steps), 21 (1 new):** real. They need the button in `_scenes.Buttons`, the exact refusal text, a saved
  deck with 1 RotA that is legal and picked, the starter, `warriors` and the collection unchanged, a reopen on the copy,
  and a second press giving `Existing` with 1 new deck. Without the feature, steps 2, 5, 7 and 8 fail.
  - Gap: the "can't fill" step calls `MakeAlleyLegal` with an injected collection. It never presses the button or draws
    the message, so the can't-fill note's on-screen look is untested.
  - Small point: "the arrows back to the starter" sets `_versusDeck` directly with `cycled: true`. It doesn't press
    `<`/`>`.
- **campaign partner lines:** real for the Tag Cup versus, the duel log and Kit with a loaner. They compare against
  `PartnerLine` and require it to differ from `Intro`.
  - Kit's "own / yours / built-in" step calls `PartnerQuote` directly, not the screen.
  - **Weak:** the guest tag step compares the screen with `PartnerQuote(...)`, the function under test. It only bites
    because of its second clause, `guestSaid != Intro`, and that clause is waived when the partner is Kit. In this run
    the partner was Ryo, so it bit.
- **Deck line "ends 70 px before the <":** **partly constant.** `gap` is computed from layout constants
  (`DeckArrowAt - 30 - DeckLineWithArrows`), not from the drawn text, so it is 70 whatever the text is. The real guard
  is `whole` (the text fits its 520-wide box). It would still fail if the box went back to 580 (gap 10).
- **Arrows end above the detail:** measured from the drawn rects. Real.
- **tag setup quotes:** `DebugQuotes()` redraws and reads what was drawn. Real.
- **layout hyphenation:** runs the real `SyllableCut`. It fails on the first cut ("Dest-ruction"). The editor name
  steps measure the drawn rects; "crusadia" needs at least 1 in-deck count, and got 9.
- **controls End/Battle Phase, recipe twice:** these pass on the old code too, as Part B says. They guard against a
  regression; they don't prove a fix.
